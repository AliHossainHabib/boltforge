نظام القوالب (Template Engine)

مرجع كامل لصياغة القوالب: المتغيرات، الشروط، وأسماء الملفات الديناميكية.

ماذا يفعل محرك القوالب؟

يحوّل أي نص (محتوى ملف، أو حتى اسم ملف/مجلد) يحتوي على صياغة خاصة إلى نص نهائي، اعتمادًا على TemplateContext (متغيرات + أعلام) المُمرَّر له. الكود كاملًا في ملفين فقط: lib/src/template_engine/template_engine.dart وtemplate_context.dart.

لماذا محرك بسيط مكتوب يدويًا بدل حزمة templating جاهزة (مثل Mustache)؟

لأن الحاجة الفعلية محدودة جدًا: استبدال متغير، وتضمين/استبعاد كتلة شرطية. لا حاجة لحلقات (loops) أو Partials أو منطق معقّد. اعتماد حزمة خارجية كاملة لهذا القدر البسيط من الوظائف يزيد التبعيات دون فائدة حقيقية.

الصياغة المدعومة بالكامل

الصياغةالمعنى
{{variableName}}استبدال بقيمة نصية من context.variables
{{ variableName }}نفس الشيء — المسافات داخل الأقواس مسموحة ويتم تجاهلها
{{#if flagName}}...{{/if}}يبقى المحتوى فقط إذا كانت قيمة العلم true
{{#unless flagName}}...{{/unless}}يبقى المحتوى فقط إذا كانت قيمة العلم false
⚠ متغير أو علم غير معروف = خطأ فوري، وليس نصًا فارغًا

استخدام {{typo}} أو {{#if nonExistentFlag}} يرمي TemplateVariableError ويوقف التوليد بالكامل. هذا قرار مقصود: متغير مفقود بصمت يعني كودًا فاسدًا يظهر لاحقًا بشكل غامض في flutter analyze بدل رسالة واضحة الآن.

أسماء الملفات والمجلدات الديناميكية

الصياغة نفسها تعمل داخل مسار الملف أيضًا، عبر renderPathSegment الذي يُطبَّق على كل جزء من المسار على حدة، ثم يحذف لاحقة .tmpl إن وُجدت:

lib/src/template_engine/template_engine.dart
String renderPathSegment(String segment) {
  final rendered = render(segment);
  return rendered.endsWith('.tmpl')
      ? rendered.substring(0, rendered.length - '.tmpl'.length)
      : rendered;
}

مثال: {{featureName}}_model.dart.tmpl ← بعد التوليد باسم offer ← offer_model.dart.

بعد كتابة الملفات، يستدعي FeatureGenerator خطوتين إضافيتين غير متعلقتين بمحرك القوالب مباشرة لكنهما جزء من نفس خط الأنابيب: DiRegistrar (تسجيل تلقائي في service_locator.dart) و FeatureValidator (تحقق بعد التوليد). التفاصيل الكاملة في صفحة توليد الـ Feature.

من أين تُقرأ هذه المجلدات فعليًا؟

⚠ هذا الجزء كان فيه خطأ حقيقي — وقد أُصلح

الإصدار الأول من هذا الحل افترض أن مجلد templates/ يقع دائمًا مستوى واحدًا فوق مكان تشغيل السكربت (bin/boltforge.dart). هذا الافتراض انهار تحديدًا عند تفعيل الأداة عالميًا (dart pub global activate)، لأن Dart تُنشئ نسخة مُصرَّفة (snapshot) في .dart_tool/pub/bin/boltforge/ — أعمق بمستوى واحد إضافي — فكان الحل القديم يحسب مسارًا غير موجود مثل ...\.dart_tool\pub\bin\templates\base ويفشل بخطأ PathNotFoundException حقيقي عند أول استخدام فعلي خارج المستودع.

الحل الصحيح يعتمد على Isolate.resolvePackageUri — الآلية نفسها التي تستخدمها Dart داخليًا لتحويل أي import 'package:boltforge/...' إلى مسار ملف حقيقي. بما أن كل استيراد في هذا البرنامج يعتمد أصلًا على نجاح هذا التحليل، فإن استخدامه لإيجاد جذر الحزمة نفسه يعمل بشكل صحيح في كل سيناريوهات التشغيل: من الكود المصدري، من نسخة snapshot مؤقَّتة (حالة pub global activate التي انكسرت)، أو من حزمة مثبَّتة فعليًا من pub.dev لاحقًا.

lib/src/core/package_paths.dart
static Future<Directory?> resolveTemplatesRoot() async {
  final root = await _resolvePackageRoot();
  if (root == null) return null;
  final templates = Directory(p.join(root.path, 'templates'));
  return templates.existsSync() ? templates : null;
}

static Future<Directory?> _resolveViaPackageConfig() async {
  final libUri = await Isolate.resolvePackageUri(
    Uri.parse('package:boltforge/boltforge.dart'),
  );
  // package:boltforge/boltforge.dart -> <root>/lib/boltforge.dart
  final libDir = Directory(p.dirname(libUri!.toFilePath()));
  final root = Directory(p.normalize(p.join(libDir.path, '..')));
  return Directory(p.join(root.path, 'templates')).existsSync() ? root : null;
}

المسار القديم المبني على Platform.script ما زال موجودًا، لكن فقط كخطة احتياطية أخيرة — ولا يُعتمَد عليه أبدًا إلا بعد التحقق فعليًا أن templates/ موجود عند المسار المُخمَّن، لا افتراضًا أعمى كما كان سابقًا.

💡 للاختبارات

كل من ProjectGenerator وFeatureGenerator يتطلبان الآن templatesRoot كمعامل إجباري (وليس اختياريًا بقيمة افتراضية داخلية) — القرار بشأن تحديد المسار أصبح بالكامل مسؤولية المستدعي. CreateCommand وGenerateCommand يحلّان المسار فعليًا عبر await PackagePaths.resolveTemplatesRoot() قبل بناء المُولِّد، بينما الاختبارات تُمرِّر مجلدًا معروفًا مباشرة (نفس مسار البناء الذي يستخدمه الإنتاج تمامًا، دون الحاجة لتزييف أي شيء). راجع صفحة الاختبارات وtest/package_paths_test.dart.

كيف تُضيف قالبًا جديدًا بالكامل؟

  1. أنشئ مجلدًا جديدًا تحت templates/ (مثلًا templates/base-v2/).
  2. ضع بداخله بنية lib/... كاملة تمامًا كما ستظهر في المشروع النهائي.
  3. أي جزء متغيّر في المحتوى أو الاسم استخدم فيه {{variableName}}.
  4. أضف أي متغير جديد تحتاجه في TemplateContext.forProject أو forFeature حسب السياق.
  5. اربط القالب الجديد من ProjectGenerator أو FeatureGenerator (استبدل أو أضف بجانب templateFor('base') الحالية).

كيف تختبر قالبًا جديدًا؟

لا تحتاج لتشغيل flutter create فعليًا لاختبار محتوى القالب — استخدم FileService وTemplateEngine مباشرة على مجلد مؤقت، كما يفعل test/auth_generation_test.dart بالضبط: 

final engine = TemplateEngine(TemplateContext.forProject(
  projectName: 'my_app', orgIdentifier: 'com.example', usesPassword: true,
));
FileService(engine).renderTree(
  templateRoot: Directory('templates/base-v2'),
  destinationRoot: tempProjectDir,
  onConflict: ConflictAction.overwrite,
);
// ثم تحقق من محتوى الملفات الناتجة مباشرة

أخطاء شائعة

الخطأالسبب
ملف يظهر باسمه الحرفي xxx.dart.tmpl على القرصلم يُستخدم renderPathSegment عند الكتابة — تحقق أنك تستخدم FileService.renderTree وليس نسخًا يدويًا.
خطأ TemplateVariableError عند التوليداستخدمت {{اسم_خاطئ}} غير معرَّف في TemplateContext المستخدَم لهذا القالب تحديدًا (فرّق بين سياق Project وسياق Feature).
كتلة {{#if}} تظهر حرفيًا في الناتج النهائيعلى الأغلب خطأ إملائي في اسم الوسم (#lf بدل #if مثلًا) — المحرك لا يتعرف عليه فيتركه كنص عادي فقط إن لم يُحلَّل كـ variable أيضًا؛ تحقق من الاسم بدقة.

معايير القبول

  • لا يوجد أي ملف بامتداد .tmpl يظهر في مشروع مُولَّد نهائيًا.
  • لا يوجد أي نص {{...}} غير مُستبدَل في أي ملف مُولَّد.
  • كل متغير مُستخدَم في قالب مُعرَّف فعليًا في TemplateContext المطابق قبل الاستخدام.
