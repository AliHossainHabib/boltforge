أنظمة تسجيل الدخول (Authentication)

شرح كامل لقالبَي المصادقة: Password و OTP، وكيف تختار بينهما.

ماذا يفعل هذا النظام؟

عند boltforge create، تختار أحد نمطين لتسجيل الدخول، فتُطبَّق مجموعة ملفات مختلفة تمامًا (شاشات، Cubit، Repository) بينما تبقى الطبقة الأساسية (ApiResult, DioClient, Routes...) واحدة في الحالتين.

لماذا نمطان منفصلان بدل نمط واحد مرن؟

لأن تدفّق Password (تسجيل دخول بكلمة مرور + نسيت كلمة المرور) وتدفّق OTP (تحقّق برمز يُرسَل، بدون كلمة مرور) يختلفان في عدد الشاشات، عدد استدعاءات الـ API، وحتى في الحالات الممكنة للـ Cubit. محاولة توحيدهما في تدفّق واحد "مرن" كانت ستُنتج كودًا مليئًا بشروط if (usesPassword) متناثرة — بدل ذلك، القالب بأكمله (الشاشات + الـ Cubit + الـ Repository) يُستبدل حسب {{#if authPassword}} / {{#if authOtp}} في الملفات المشتركة (routes.dart, app_router.dart, splash_screen.dart)، وملفات كاملة منفصلة لكل نمط.

نمط Password

templates/auth/password/lib/features/auth/ ├── model/user_model.dart.tmpl ├── repository/auth_repository.dart.tmpl login / register / forgotPassword / resetPassword ├── cubit/ │ ├── auth_cubit.dart.tmpl login() / register() / forgotPassword() │ └── auth_state.dart.tmpl Initial / Loading / Success / Failure └── presentation/screen/ ├── login_screen.dart.tmpl ├── register_screen.dart.tmpl └── forgot_password_screen.dart.tmpl

مخطط التدفق

Login
 ↓
Email/Phone + Password
 ↓
AuthCubit.login()
 ↓
AuthRepository.login() → POST ApiConstants.login
 ↓
نجاح؟ → تخزين token → AuthSuccess → Navigator إلى Routes.home
فشل؟  → AuthFailure(ApiError) → SnackBar

مثال كود حقيقي: AuthCubit.login

templates/auth/password/.../cubit/auth_cubit.dart.tmpl
Future<void> login({required String email, required String password}) async {
  emit(const AuthLoading());
  final result = await _repository.login(email: email, password: password);
  if (result.success && result.data != null) {
    emit(AuthSuccess(result.data!));
  } else {
    emit(AuthFailure(result.error ?? const ApiError(code: 'unknown', messageKey: 'err_unknown')));
  }
}

نمط OTP

templates/auth/otp/lib/features/auth/ ├── model/user_model.dart.tmpl ├── repository/auth_repository.dart.tmpl requestOtp / verifyOtp / completeProfile ├── cubit/ │ ├── auth_cubit.dart.tmpl │ └── auth_state.dart.tmpl + OtpSent(accountExists) + VerifiedNeedsProfile └── presentation/screen/ ├── verification_screen.dart.tmpl └── create_account_screen.dart.tmpl

مخطط التدفق (يطابق الطلب الأصلي بالضبط)

Start
 ↓
Verification Screen (إدخال Email أو Phone)
 ↓
AuthCubit.requestOtp() → Repository.requestOtp()
 ↓
الخادم يُرجع accountExists: true/false + يرسل رمز التحقق
 ↓
المستخدم يُدخل الرمز → AuthCubit.verifyOtp()
 ↓
Account exists?
 ├── YES → AuthSuccess(user) مباشرة → Home
 └── NO  → VerifiedNeedsProfile → CreateAccountScreen (اسم فقط) → completeProfile() → Home
⚠ افتراض على عقد الـ Backend

هذا التدفق يفترض أن نقطة النهاية ApiConstants.requestOtp تُرجع حقل accountExists ضمن data. إن كان الـ backend لديك لا يدعم هذا الحقل، عدّل AuthRepository.requestOtp في templates/auth/otp/.../repository/auth_repository.dart.tmpl ليطابق عقدك الفعلي — هذا الافتراض لم يُختبر ضد backend حقيقي بعد.

الاختيار بين النمطين: أين تُقرأ القيمة؟

القيمة usesPassword تتحول إلى علمين متعاكسين دومًا:

lib/src/template_engine/template_context.dart
flags: {
  'authPassword': usesPassword,
  'authOtp': !usesPassword,
},

وتُستخدم هذه الأعلام في الملفات المشتركة لتضمين/استبعاد أجزاء كاملة، مثال من routes.dart.tmpl: 

{{#if authPassword}}
  static const String login = '/login';
  static const String register = '/register';
  static const String forgotPassword = '/forgot-password';
{{/if}}
{{#if authOtp}}
  static const String verify = '/verify';
  static const String createAccount = '/create-account';
{{/if}}

كيف تُضيف طريقة تحقق ثالثة (مثلًا: Social Login)؟

  1. أنشئ مجلدًا جديدًا templates/auth/social/ بنفس بنية password/otp.
  2. أضف علمًا جديدًا (authSocial) في TemplateContext.forProject، وحدّث منطق usesPassword الثنائي الحالي ليصبح enum بثلاث قيم بدل bool.
  3. حدّث --auth في CreateCommand ليقبل القيمة الجديدة ضمن allowed: ['password', 'otp', 'social'].
  4. حدّث ProjectGenerator ليختار مجلد القالب الصحيح بدل usesPassword ? 'password' : 'otp'.
  5. أضف اختبارات جديدة في test/auth_generation_test.dart بنفس أسلوب مجموعتي "Password authentication generation" و"OTP authentication generation".

أخطاء شائعة

الخطأالسبب
ظهور شاشتي login و verification معًالن يحدث فعليًا — القالبان متنافيان بالكامل ولا يُطبَّقان معًا أبدًا، لكن تأكد أنك لم تُعدّل ProjectGenerator يدويًا لتطبيق كليهما.
استيراد مفقود لـ LoginScreen في app_router.dartتأكد أن قيمة usesPassword الممرَّرة للقالب مطابقة لما اخترته فعليًا عند create.

معايير القبول

  • مشروع أُنشئ بـ --auth=password يحتوي على login_screen.dart ولا يحتوي إطلاقًا على verification_screen.dart.
  • مشروع أُنشئ بـ --auth=otp والعكس تمامًا.
  • routes.dart في كل حالة يحتوي فقط على ثوابت النمط المختار.
