الأمر المستخدَم للتحقق (شغّله بنفسك عند أي تعديل)

cd boltforge
dart pub get
dart format .
dart analyze
dart test

ماذا تفعل مجموعة الاختبارات؟

13 ملف اختبار في test/ يغطي كل طبقة في الأداة، مع تركيز صريح على التحقق من محتوى ملفات حقيقية (أسماء أصناف، مسارات استيراد، بنية مجلدات) بدل اختبارات سطحية تتحقق فقط من عدم رمي استثناء.

لماذا هذا مهم تحديدًا لأداة توليد كود؟

أداة مثل boltforge لا "تُرجع قيمة" يمكن فحصها بسهولة — نتيجتها الحقيقية هي ملفات على القرص. اختبار سطحي ("الدالة لم تنهَر") لا يكشف خطأ مثل استيراد بمسار خاطئ، أو اسم صنف بحرف صغير بدل كبير. لذلك كل اختبار توليد هنا يقرأ الملف الناتج فعليًا من القرص (File(...).readAsStringSync()) ويتحقق من محتواه حرفيًا.

test('generated cubit imports its own state, model, and repository files correctly', () {

هذا الاختبار كان سيكشف فورًا لو أن أحد مسارات الاستيراد النسبية في القالب كان خاطئًا بعمق واحد فقط — وهو خطأ شائع جدًا عند تعديل بنية المجلدات.

كيف تعمل الاختبارات بدون Flutter مثبَّت؟

عبر حقن التبعيات: FeatureGenerator وProjectGenerator يقبلان templatesRoot اختياريًا (بدل الاعتماد فقط على Platform.script)، وProjectGenerator يقبل ProcessService قابلًا للاستبدال بـ FakeProcessService (في test/support/fake_process_service.dart) — بديل حقيقي يسجّل كل استدعاء ويُرجع نتائج قابلة للتحكّم دون تشغيل أي عملية فعلية.

test/support/fake_process_service.dart
class FakeProcessService implements ProcessService {
  final List<RecordedCall> calls = [];
  // ...
  @override
  Future<ProcessOutcome> run(String executable, List<String> args, {String? workingDirectory}) async {
    calls.add(RecordedCall(executable, args, workingDirectory));
    final onRun = _onRun;
    return onRun != null ? onRun(executable, args) : _defaultOutcome;
  }
}

بُنية اختبار توليد نموذجية (نمط متكرر في كل اختبارات التوليد)

setUp(() {
  tempDir = Directory.systemTemp.createTempSync('boltforge_..._test_');
});

tearDown(() {
  if (tempDir.existsSync()) tempDir.deleteSync(recursive: true);
});

كل اختبار يعمل على مجلد مؤقت معزول تمامًا، ويُحذف بعد الاختبار — لا أثر يبقى على القرص.

كيف تُضيف اختبارًا جديدًا؟

  1. حدّد أي طبقة تختبرها (Service? Generator? Command?) واختر الملف المطابق أو أنشئ ملفًا جديدًا بنفس الاسم + _test.dart.
  2. إن كان الاختبار يحتاج نظام ملفات، استخدم Directory.systemTemp.createTempSync(...) في setUp واحذفه في tearDown.
  3. إن كان يحتاج عملية خارجية (flutter/dart)، استخدم FakeProcessService بدل الحقيقي.
  4. اكتب الـ assertion على محتوى فعلي (ملف، نص، بنية) وليس فقط "لم يرمِ استثناء".
  5. شغّل dart test test/<file>.dart للملف تحديدًا أثناء التطوير.

الاعتماد على PackagePaths.resolveTemplatesRoot() الحقيقي داخل اختبار بدل حقن مسار معروفيعمل صحيحًا الآن فعليًا تحت dart test (راجع package_paths_test.dart)، لكن الأسرع والأبسط لبقية الاختبارات هو حقن Directory.current/templates مباشرة بدل انتظار عملية async غير ضرورية.

اختبار يعتمد على وجود Flutter الحقيقي مثبَّتًايجعل الاختبار غير قابل للتشغيل على أي جهاز CI بدون Flutter — استخدم FakeProcessService.
