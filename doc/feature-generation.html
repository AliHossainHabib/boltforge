كيف أضيف Feature Generator جديدة؟

درس شامل من الصفر: كيف يعمل boltforge generate offer بالضبط، ملفًا ملفًا — بما في ذلك التسجيل التلقائي في GetIt والتحقق بعد التوليد — وكيف تُعدّل أو تُوسّع هذا السلوك بنفسك.

ماذا يفعل هذا الأمر؟

عند تشغيل هذا الأمر داخل مشروع Flutter موجود:

cd my_app
boltforge generate offer

يقوم الأمر بأربعة أشياء بالترتيب:

  1. يُنشئ البنية الكاملة داخل lib/features/offer/.
  2. يُسجّل OfferRepository تلقائيًا في lib/core/di/service_locator.dart.
  3. يتحقق من النتيجة (لا ملفات ناقصة، لا .tmpl متسرّب، لا placeholder غير محلول، لا تسجيل مكرَّر).
  4. يطبع تقريرًا كاملًا — بما في ذلك أي مشكلة وجدها.
lib/features/offer/ ├── cubit/ │ ├── offer_cubit.dart │ └── offer_state.dart ├── repository/ │ └── offer_repository.dart ├── model/ │ └── offer_model.dart └── presentation/ ├── screen/ │ └── offer_screen.dart └── widgets/ └── offer_list_item.dart

لماذا lib/features/offer/ وليس lib/offer/؟

كل Feature في التطبيق — سواء كانت مُولَّدة من الإطار (مثل auth عبر create) أو مُولَّدة يدويًا لاحقًا (مثل offer عبر generate) — تعيش الآن تحت مسار واحد موحَّد: lib/features/<name>/. هذا يجعل أي مطوّر ينظر إلى lib/ يرى فورًا "كل الـ Features هنا"، بدل البحث في جذر lib/ نفسه عن مجلدات متفرقة.

الخطوة صفر: من أين تبدأ الرحلة في الكود؟

  1. bin/boltforge.dart → BoltforgeRunner().run(arguments)
  2. lib/src/cli_runner.dart → يوجّه generate إلى GenerateCommand
  3. lib/src/commands/generate_command.dart → GenerateCommand.run()
  4. lib/src/generators/feature_generator.dart → FeatureGenerator.generate() — هذا هو المنسِّق الفعلي لكل الخطوات القادمة.

الخطوة 1: التحقق من الاسم، ثم من المشروع

نفس الفحصين المعتادين: NameValidator (اسم صالح lower_snake_case) ثم ProjectDetector (نحن فعلًا داخل مشروع Flutter). لا جديد هنا — التفاصيل في صفحة أوامر الـ CLI.

الخطوة 2: توليد الملفات (كما كان، بمسار جديد)

lib/src/generators/feature_generator.dart
final destinationRoot = Directory(p.join(projectRoot.path, 'lib', 'features'));

final plannedPaths = fileService.planOutputPaths(templateDir);
final alreadyExists = plannedPaths.any(
  (relative) => File(p.join(destinationRoot.path, relative)).existsSync(),
);

var conflictAction = ConflictAction.overwrite;
if (alreadyExists) {
  conflictAction = onExistingFeature(featureName); // يسأل المستخدم
  if (conflictAction == ConflictAction.cancel) {
    return const FeatureGenerationResult(wasCancelled: true, ...);
  }
}

final written = fileService.renderTree(
  templateRoot: templateDir,
  destinationRoot: destinationRoot, // lib/features/
  onConflict: conflictAction,
);

إن كانت Feature بنفس الاسم موجودة، تظهر لك ثلاثة خيارات كما كان:

الخيارالسلوك الفعلي في FileService.renderTree
Cancelلا تُكتب أي ملفات إطلاقًا، ولا يُلمَس DI إطلاقًا.
Overwriteكل ملف من القالب يُعاد كتابته، حتى لو كنت قد عدّلته يدويًا.
Mergeيُكتب فقط الملف غير الموجود؛ أي ملف موجود مسبقًا يبقى كما هو.

الخطوة 3: التسجيل التلقائي في GetIt — كيف يعمل بالضبط؟

هذه الخطوة الجديدة. بعد كتابة الملفات، يحسب FeatureGenerator اسم صنف الـ Repository ومسار استيراده، ثم يستدعي DiRegistrar:

lib/src/generators/feature_generator.dart
final nameCase = NameCase.from(featureName);
final repositoryClassName = '${nameCase.pascal}Repository'; // OfferRepository
final repositoryImportPath =
    '../../features/${nameCase.snake}/repository/${nameCase.snake}_repository.dart';

final diResult = diRegistrar.registerRepository(
  serviceLocatorFile: File(p.join(projectRoot.path, 'lib/core/di/service_locator.dart')),
  repositoryClassName: repositoryClassName,
  importPath: repositoryImportPath,
);

لماذا ليس تحليل AST كامل لملف Dart؟

لأن service_locator.dart ملف تُنشئه boltforge نفسها من قالبها الخاص — نتحكم في شكله بالكامل. بدل الاعتماد على حزمة analyzer ثقيلة لتحليل الشجرة النحوية، وضعنا تعليقَي ترسيخ ثابتَين داخل القالب نفسه:

templates/base/lib/core/di/service_locator.dart.tmpl
import 'package:get_it/get_it.dart';

import '../../features/auth/repository/auth_repository.dart';
// boltforge:imports

final GetIt sl = GetIt.instance;

void configureDependencies() {
  sl.registerLazySingleton<AuthRepository>(() => AuthRepository());
  // boltforge:registrations
}

DiRegistrar يبحث عن هذين التعليقَين ويُدرج السطر الجديد قبلهما مباشرة، ثم يعيد كتابة التعليق نفسه بعد الإدراج — بحيث يبقى نقطة إدراج صالحة للمرة القادمة. هذا يعني أن توليد Feature عاشرة يعمل بنفس موثوقية الأولى.

الحماية من التكرار (Duplicates)

قبل أي إدراج، يتحقق DiRegistrar من وجود السطر مسبقًا:

final alreadyImported = content.contains("import '$importPath';");
final alreadyRegistered = content.contains('registerLazySingleton<$repositoryClassName>');

if (alreadyImported && alreadyRegistered) {
  return const DiRegistrationResult(status: DiRegistrationStatus.registered); // لا تغيير
}

لذلك: تشغيل boltforge generate offer مرتين (باختيار Overwrite عند التعارض) لا يُنتج سطرَين مكرَّرين في service_locator.dart أبدًا.

الحالات الآمنة عند الفشل

الحالةماذا يحدث
service_locator.dart غير موجود إطلاقًا حالة fileMissing — تحذير واضح في الطرفية، الميزة نفسها لا تزال تُولَّد بنجاح، والخروج بالكود 0.
الملف موجود لكن تعليقَي الترسيخ غير موجودين (مثلًا مطوّر أعاد كتابة الملف يدويًا) حالة markersMissing — الأداة لا تخمّن مكان الإدراج ولا تلمس الملف إطلاقًا، وتطبع تحذيرًا يطلب منك التسجيل يدويًا.

الخطوة 4: التحقق بعد التوليد (Post-Generation Validation)

بعد التوليد والتسجيل، يشغّل FeatureGenerator فحصًا أخيرًا عبر FeatureValidator — شبكة أمان إضافية، وليست بديلًا عن رمي TemplateEngine لخطأ فوري عند متغير غير معروف:

lib/src/services/feature_validator.dart
  • ملفات ناقصة: أي مسار متوقَّع من القالب ولم يُكتب فعليًا → خطأ.
  • ملفات .tmpl متسرّبة: أي ملف بقي بامتداده الأصلي بدل أن يُعاد تسميته → خطأ.
  • placeholders غير محلولة: أي ملف مولَّد يحتوي على {{ حرفيًا → خطأ.
  • Repository غير مسجَّلة: صفر تكرارات لـ registerLazySingleton<X> → تحذير (وليس خطأ، لأن هذا وضع مُتوقَّع عند غياب service_locator.dart).
  • تسجيل مكرَّر: أكثر من تكرار واحد → خطأ (يعني تلفًا يدويًا سابقًا في الملف، وليس نتيجة طبيعية لعمل الأداة).

الفرق بين خطأ وتحذير يحدد رمز الخروج: أي خطأ واحد يجعل boltforge generate يُنهي بالكود 1 (حتى لو كُتبت الملفات بنجاح) — لأن هذا يعني وجود مشكلة حقيقية تستحق الانتباه.

محتوى service_locator.dart قبل وبعد (مثال كامل)

قبل تشغيل boltforge generate offer:

void configureDependencies() {
  sl.registerLazySingleton<AuthRepository>(() => AuthRepository());
  // boltforge:registrations
}

بعد:

void configureDependencies() {
  sl.registerLazySingleton<AuthRepository>(() => AuthRepository());
  sl.registerLazySingleton<OfferRepository>(() => OfferRepository());
  // boltforge:registrations
}

لا تدخل يدوي مطلوب على الإطلاق.

كيف تُعدّل ما تولّده الأداة؟

  1. لتغيير شكل الحالات (State) الافتراضية: عدّل templates/feature/{{featureName}}/cubit/{{featureName}}_state.dart.tmpl.
  2. لإضافة دالة جديدة لكل Repository مولَّدة تلقائيًا: عدّل {{featureName}}_repository.dart.tmpl.
  3. لإضافة widget افتراضي آخر داخل presentation/widgets/: أنشئ ملف .tmpl جديدًا هناك — سيُنسخ تلقائيًا لكل Feature قادمة.
  4. لتغيير آلية التسجيل في GetIt نفسها: عدّل lib/src/services/di_registrar.dart (احذر: لا تغيّر نص تعليقَي الترسيخ هنا دون تحديث القالب أيضًا).
  5. لإضافة فحص تحقق جديد بعد التوليد: أضِفه في lib/src/services/feature_validator.dart.

كيف تختبر تعديلك؟

لا تحتاج مشروع Flutter حقيقي ولا Flutter مثبَّتًا لاختبار أي جزء من هذا — كل شيء (التوليد، DI، التحقق) يعمل على ملفات ومجلدات مؤقتة حقيقية:

الملفيغطي
test/feature_generator_test.dartالتوليد كاملًا (بنية، أصناف، استيرادات) + تكامل DI والتحقق
test/di_registrar_test.dartDiRegistrar وحده: إدراج، عدم تكرار، تعامل آمن مع ملف مفقود/معدَّل يدويًا
dart test test/feature_generator_test.dart test/di_registrar_test.dart

أخطاء شائعة عند إضافة أو تعديل Feature Generator

الخطألماذا يحدث ولماذا هو خطير
نسيان تحديث عمق مسار الاستيراد النسبي بعد تغيير عمق المجلد كل ملف .tmpl يعتمد على عمقه الدقيق داخل lib/features/<feature>/.... إضافة مجلد فرعي جديد يغيّر العمق ويكسر كل الاستيرادات دفعة واحدة.
حذف تعليق // boltforge:imports أو // boltforge:registrations من القالب يوقف DiRegistrar بالكامل — سيُرجع markersMissing لكل مشروع جديد.
استخدام متغير غير معرَّف في TemplateContext لن يُترجَم الملف مطلقًا — TemplateEngine يرمي TemplateVariableError عمدًا بدل تجاهل المتغير بصمت.
افتراض أن Merge "يدمج محتوى الملفين" Merge لا يدمج المحتوى إطلاقًا — فقط يقرر أي الملفات (كوحدة كاملة) تُكتب وأيها يبقى.

معايير القبول

  • boltforge generate offer ينتج ستة ملفات بالضبط تحت lib/features/offer/.
  • OfferRepository مسجَّلة تلقائيًا في service_locator.dart — مرة واحدة بالضبط.
  • كل استيراد داخل الملفات المولَّدة يُشير إلى مسار موجود فعليًا (يتحقق منه flutter analyze).
  • تشغيل الأمر مرتين على نفس الاسم لا يُنتج تسجيل DI مكرَّرًا، ولا يحذف شيئًا تلقائيًا.
  • اسم غير صالح يُرفض بالكود 64 قبل لمس أي ملف أو أي تعديل على DI.
  • أي مشكلة حقيقية (تسجيل مكرَّر، ملف ناقص) تُنهي الأمر بالكود 1 مع رسالة واضحة — لا نجاح صامت أبدًا.
