المساهمة في المشروع

كيف تضيف كودًا لهذا المشروع بأسلوب يتوافق مع قواعده الحالية.

✔ تم إنشاء ملف CONTRIBUTING.md فعليًا

هذه الصفحة تشرح القواعد بتفصيل أكبر مع أمثلة، لكن الملف المرجعي الذي يظهره GitHub تلقائيًا عند فتح Issue أو Pull Request هو CONTRIBUTING.md في جذر المستودع — وهو موجود الآن ويحيل إلى هذه الصفحة للتفاصيل الكاملة.

القواعد المعمارية الملزمة

  1. لا Cubit يُسجَّل في GetIt أبدًا — فقط الـ Repositories (راجع صفحة المعمارية).
  2. كل استدعاء لعملية خارجية (flutter/dart) يمر عبر ProcessService — أبدًا Process.run مباشرة داخل command أو generator.
  3. كل مسار قوالب يجب أن يكون قابلًا للحقن — أي generator أو command جديد يقرأ من templates/ يجب أن يقبل templatesRoot إجباريًا في مُنشئه (وليس اختياريًا بقيمة افتراضية داخلية — راجع صفحة نظام القوالب لسبب هذا القرار).
  4. لا كتابة صامتة فوق ملفات موجودة — أي عملية توليد تواجه ملفًا موجودًا يجب أن تمر عبر آلية ConflictAction (cancel/overwrite/merge)، لا استبدال تلقائي بصمت.
  5. متغيرات القالب المفقودة = خطأ فوري — لا تُرجع أبدًا سلسلة فارغة بدل رمي TemplateVariableError.

أسلوب الكود

  • يتّبع analysis_options.yaml في جذر المشروع (يستند إلى package:lints/recommended.yaml).
  • علامات اقتباس مفردة ('single quotes') وليست مزدوجة.
  • كل دالة عامة يجب أن يكون نوع إرجاعها معلنًا صراحة (always_declare_return_types).
  • تعليقات /// (doc comments) على كل صنف/دالة عامة تشرح لماذا وليس فقط ماذا.

قبل إرسال أي تعديل

terminal
dart format .
dart analyze
dart test

لا يُقبل أي تعديل لا يمر بهذه الأوامر الثلاثة بدون أخطاء — وهي تُشغَّل فعليًا على كل Pull Request عبر CI (راجع صفحة الاختبارات).

إضافة اختبار مع كل تعديل سلوكي

أي تغيير في سلوك ملحوظ (مسار جديد، خيار CLI جديد، حقل قالب جديد) يجب أن يرافقه اختبار حقيقي يتحقق من محتوى فعلي — وليس فقط "الدالة لم تنهَر". راجع صفحة الاختبارات للنمط المتَّبع بالضبط.

إضافة Feature أو Auth mode جديد

اتبع الأدلة المخصصة لكل حالة بالتفصيل الكامل:

  • كيف أضيف Feature Generator جديدة؟
  • كيف أضيف طريقة مصادقة جديدة؟
  • كيف أضيف قالبًا جديدًا بالكامل؟

أخطاء شائعة عند المساهمة

الخطألماذا يُرفَض
تعديل قالب بدون اختبار مطابق في test/خطأ في مسار استيراد قد يمر دون ملاحظة حتى يصطدم به مستخدم فعلي.
إضافة تبعية جديدة للأداة نفسها بدون سبب واضح موثَّقكل تبعية إضافية تزيد وقت dart pub get وسطح الهجوم الأمني — يجب أن تكون ضرورية فعلًا.
كتابة منطق توليد ملفات مباشرة داخل ملف commands/يكسر فصل المسؤوليات — يجب أن يبقى في generators/.

معايير القبول لأي Pull Request

  • dart format . لم يُغيّر أي ملف (الكود مُنسَّق مسبقًا).
  • dart analyze بدون أي تحذير أو خطأ.
  • dart test ناجح بالكامل.
  • كل سلوك جديد موثَّق في صفحة التوثيق المناسبة (وليس فقط في تعليق كود).
